Cada tópico responde cinco coisas: o que é, por que usar, onde aparece no projeto (com código real), prós e contras, e uma frase pronta para você falar em entrevista ou reunião.

Começo

Visão geral em 1 minuto

É uma API REST em .NET 10 que controla o estoque de restaurantes: produtos, categorias, fornecedores e movimentações (entrada e saída). Vários restaurantes usam a mesma API e o mesmo banco, mas cada um só enxerga os próprios dados.

AssuntoO que o projeto usa
ArquiteturaClean Architecture em 5 projetos (Domain, Application, Infrastructure, Api, Contracts)
DomínioDDD com entidades ricas, factory methods e DomainException
Casos de usoCQRS com MediatR (Commands, Queries, Handlers)
ValidaçãoFluentValidation + ValidationBehavior no pipeline do MediatR
DadosEF Core + SQL Server, Repository Pattern, NoTracking global, tabelas criadas por script SQL
EndpointsMinimal API organizada em IEndpointModule, rotas /api/v1/..., Swagger
SegurançaJWT Bearer, ASP.NET Core Identity, roles Admin/Funcionario, isolamento por RestaurantId
TestesxUnit + EF Core InMemory + dublês (Fakes)
Como falar: “É uma API de estoque multi-restaurante em .NET 10, com Clean Architecture, CQRS via MediatR e DDD. As regras de negócio ficam nas entidades, a validação de entrada roda num pipeline do MediatR, e o acesso a dados passa por repositórios que já filtram pelo restaurante do usuário logado.”
Começo

Caminho de uma requisição

Exemplo: o frontend chama POST /api/v1/products para criar um produto. Isso é o que acontece, em ordem:

flowchart TD
  A[Navegador / Next.js] -->|POST /api/v1/products + Bearer token| B[Middlewares: ExceptionHandler, CORS, Authentication, Authorization]
  B --> C[ProductEndpointsModule]
  C -->|mediator.Send CreateProductCommand| D[ValidationBehavior + FluentValidation]
  D -->|válido| E[CreateProductHandler]
  E --> F[Product.Create no Domain]
  E --> G[IProductRepository.Add]
  E --> H[IApplicationDbContext.SaveChangesAsync]
  H --> I[(SQL Server)]
  D -.->|inválido: ValidationException| B
  F -.->|regra quebrada: DomainException| B
  • Middlewares conferem o token e a permissão antes de chegar no endpoint.
  • O endpoint só traduz HTTP para um Command e chama o MediatR.
  • O ValidationBehavior valida a entrada. Se falhar, o Handler nem roda.
  • O Handler monta a entidade pelo factory method, pede ao repositório para adicionar e salva.
  • Se der erro em qualquer ponto, o middleware de exceções converte em 400, 401, 404 ou 500.
Arquitetura

Clean Architecture (camadas)

O que é

Separar o código em camadas, onde as dependências sempre apontam para dentro, em direção ao domínio. O centro (regras de negócio) não sabe nada de banco, HTTP ou frameworks.

flowchart LR
  Api --> Application
  Api --> Infrastructure
  Infrastructure --> Application
  Application --> Domain
  Api --> Contracts
  Application --> Contracts
  Infrastructure --> Contracts
ProjetoResponsabilidadeSabe de EF Core / HTTP?
DomainEntidades (Product, Category...), regras de negócio, DomainExceptionNão. C# puro.
ApplicationCasos de uso (Commands/Queries/Handlers), validators, interfaces (IProductRepository, IClock...)Não. Desde a Etapa 18b nem referencia EF Core.
InfrastructureImplementações: AppDbContext, repositórios, Identity, JWT, ClockSim, é aqui que mora o EF Core.
ApiProgram.cs, endpoints, middlewares, SwaggerSim, HTTP.
ContractsDTOs de entrada e saída (ProductDetailsDto, RoleNames...)Não.

Por que usar

Trocar o banco, o framework web ou a forma de autenticação mexe só nas camadas de fora. As regras de negócio ficam protegidas e testáveis sem subir banco nem servidor.

No projeto

A Application declara a interface e a Infrastructure implementa. Isso é a inversão de dependência na prática:

Application/Abstractions/Repositories/IProductRepository.cs → implementada em Infrastructure/Persistence/Repositories/ProductRepository.cs
// Application só conhece o contrato:
public interface IProductRepository
{
    Task<Product?> GetByIdAsync(Guid id, CancellationToken ct);
    void Add(Product product);
    void Update(Product product);
    void Remove(Product product);
}

// Infrastructure sabe que existe EF Core por trás:
public class ProductRepository : IProductRepository
{
    private readonly AppDbContext _context;
    public void Add(Product product) => _context.Products.Add(product);
}
Prós
  • Domínio isolado e fácil de testar
  • Troca de tecnologia com impacto pequeno
  • Cada coisa tem um lugar óbvio
Contras
  • Mais projetos, pastas e arquivos
  • Para um CRUD simples parece burocrático
  • Curva de aprendizado para quem chega
Como falar: “Uso Clean Architecture: o Domain não depende de nada, a Application define interfaces e a Infrastructure implementa. Por isso a Application nem referencia o EF Core.”
Arquitetura

DDD e entidades ricas

O que é

Domain-Driven Design coloca as regras de negócio dentro das entidades. Uma entidade rica tem comportamento (métodos) e protege o próprio estado. O oposto é a entidade anêmica: só propriedades com get; set;, e as regras espalhadas pelos serviços.

No projeto

  • Setters são private set: ninguém de fora muda QuantityInStock na mão.
  • O construtor é privado; só se cria pelo Product.Create(...), que valida tudo (invariantes).
  • Mudança de estoque só pelos métodos IncreaseStock/DecreaseStock.
Domain/Entities/Product.cs
public class Product : Entity
{
    public int QuantityInStock { get; private set; }

    private Product() { }

    public void DecreaseStock(int quantity)
    {
        ValidateMovementQuantity(quantity);

        if (quantity > QuantityInStock)
            throw new DomainException(
                $"Estoque insuficiente: disponível {QuantityInStock}, solicitado {quantity}.");

        QuantityInStock -= quantity;
    }
}

Invariante é uma regra que nunca pode ser quebrada, como “estoque não fica negativo”. Como a regra está na entidade, não importa quem chame: ela sempre vale.

Prós
  • Impossível existir um objeto inválido em memória
  • Regra num lugar só, sem duplicar
  • Testes de domínio simples, sem banco
Contras
  • EF Core precisa de construtor privado e mapeamento cuidadoso
  • Mais código que um POCO com get; set;
  • Para telas puramente CRUD o ganho é menor
Como falar: “As entidades são ricas: setters privados, factory method que valida as invariantes e métodos de negócio como DecreaseStock, que lança DomainException se faltar estoque.”
Arquitetura

CQRS

O que é

Command Query Responsibility Segregation: separar operações que mudam estado (Commands) das que só leem (Queries). Cada uma tem seu modelo e seu Handler.

TipoExemplos no projetoDevolve
CommandCreateProductCommand, UpdateProductCommand, DeleteProductCommand, CreateStockMovementCommand, LoginCommandId criado, token, ou nada
QueryGetProductsQuery (paginada e ordenada), GetProductByIdQueryDTOs (ProductListItemDto, ProductDetailsDto)
Application/UseCases/Products/Commands/CreateProduct/CreateProductCommand.cs
// Envelope de dados que representa uma intenção.
// IRequest<Guid> = quem tratar isso devolve um Guid (Id do produto).
public record CreateProductCommand(
    string Name,
    string? Description,
    decimal Price,
    Guid CategoryId,
    int InitialQuantity = 0) : IRequest<Guid>;

Aqui o CQRS é a versão leve: mesmo banco para leitura e escrita. A versão “pesada” usa bancos separados, eventos e consistência eventual, o que este projeto não precisa.

Prós
  • Cada caso de uso é uma classe pequena e focada
  • Leitura pode ser otimizada sem mexer na escrita
  • Fácil achar o código: um caso de uso, uma pasta
Contras
  • Muitos arquivos (Command + Handler + Validator por ação)
  • Exagero em sistemas muito pequenos
  • Quem confunde com Event Sourcing complica sem motivo
Como falar: “Uso CQRS no nível de código, não de infraestrutura: Commands mudam estado, Queries devolvem DTOs, os dois sobre o mesmo SQL Server.”
Arquitetura

Organização da camada Application

Quatro pastas de topo, inspiradas num projeto real da empresa:

Application/
├─ Abstractions/   → interfaces (Repositories/ e Services/)
├─ Common/         → Behaviors/, Exceptions/, Models/ (PagedResult)
├─ UseCases/       → Products/Commands/CreateProduct/..., Products/Queries/...
└─ Validators/     → um arquivo por validator do FluentValidation

Dentro de UseCases/ cada caso de uso tem sua própria pasta. Isso lembra Vertical Slice: tudo de “criar produto” está junto, em vez de espalhado em pastas por tipo técnico.

Prós
  • Achar um caso de uso é direto
  • Interfaces num só lugar deixam claro o que a Infrastructure precisa entregar
Contras
  • Validators fora da pasta do caso de uso exigem using extra
  • Pastas profundas, caminhos longos
Design pattern · Comportamental

Mediator (MediatR)

O que é

Um objeto do meio recebe a mensagem e entrega para quem sabe tratá-la. Quem envia não conhece quem recebe. O endpoint chama mediator.Send(command) e o MediatR acha o Handler certo.

Application/UseCases/Products/Commands/CreateProduct/CreateProductHandler.cs
public class CreateProductHandler : IRequestHandler<CreateProductCommand, Guid>
{
    public async Task<Guid> Handle(CreateProductCommand request, CancellationToken ct)
    {
        var product = Product.Create(
            request.Name, request.Description, request.Price, request.CategoryId,
            _clock.UtcNow, request.InitialQuantity, _currentUserService.RestaurantId);

        _productRepository.Add(product);
        await _context.SaveChangesAsync(ct);

        return product.Id;
    }
}

O registro é automático: RegisterServicesFromAssembly varre o projeto e registra todos os Handlers.

Prós
  • Endpoint fino, sem lógica
  • Permite pipeline behaviors (validação, log) para todos os casos de uso
  • Baixo acoplamento entre Api e Application
Contras
  • Indireção: “Ir para definição” no Send não leva ao Handler
  • Biblioteca externa (versões novas do MediatR passaram a ter licença comercial)
  • Pequeno custo de reflexão
Como falar: “O MediatR implementa o padrão Mediator: o endpoint envia um Command e não sabe qual Handler vai tratar. Isso me dá um ponto único para plugar comportamentos como validação.”
Design pattern · Estrutural

Pipeline Behavior (Decorator / Chain of Responsibility)

O que é

Um código que “embrulha” o Handler e roda antes ou depois dele. É a ideia do Decorator (adicionar comportamento sem mexer na classe) organizada como uma corrente, onde cada elo chama next().

Application/Common/Behaviors/ValidationBehavior.cs
public async Task<TResponse> Handle(TRequest request,
    RequestHandlerDelegate<TResponse> next, CancellationToken ct)
{
    if (!_validators.Any())
        return await next();          // sem validator: segue direto

    var results = await Task.WhenAll(
        _validators.Select(v => v.ValidateAsync(new ValidationContext<TRequest>(request), ct)));

    var failures = results.SelectMany(r => r.Errors).ToList();
    if (failures.Count > 0)
        throw new ValidationException(failures);   // Handler nem é chamado

    return await next();              // tudo certo: chama o Handler
}

Registrado uma vez com cfg.AddOpenBehavior(typeof(ValidationBehavior<,>)) e vale para todo Command e Query.

Prós
  • Preocupações transversais (validação, log, transação) num lugar só
  • Handlers ficam limpos
  • Adicionar um behavior novo não mexe em nenhum Handler
Contras
  • Comportamento “invisível” para quem lê só o Handler
  • A ordem de registro dos behaviors importa
Como falar: “A validação é uma preocupação transversal, então fica num pipeline behavior do MediatR. Ele roda os validators antes do Handler e lança ValidationException se algo falhar.”
Design pattern · Acesso a dados

Repository + Unit of Work

O que é

Repository esconde como os dados são buscados e gravados, oferecendo métodos com nome de negócio (GetByIdAsync, Add). Unit of Work junta várias mudanças e grava todas de uma vez, numa transação.

No projeto

O repositório só marca o que mudou. Quem grava é o IApplicationDbContext.SaveChangesAsync, que faz o papel de Unit of Work. Na movimentação de estoque, isso garante que a movimentação e o novo estoque do produto sejam gravados juntos.

// CreateStockMovementHandler (resumido)
product.DecreaseStock(request.Quantity);
_productRepository.Update(product);
_stockMovementRepository.Add(movement);
await _context.SaveChangesAsync(ct);   // uma transação para as duas mudanças

Bônus: o repositório também concentra o filtro do restaurante (multi-tenant), então nenhum Handler esquece de filtrar.

return await _context.Products
    .Include(p => p.Category)
    .Where(p => p.RestaurantId == _currentUserService.RestaurantId)
    .FirstOrDefaultAsync(p => p.Id == id, ct);
Prós
  • Application não depende do EF Core
  • Fácil de trocar por Fake nos testes
  • Lugar único para regras de consulta (filtro de tenant, Include, ordenação)
Contras
  • O DbContext já é um Repository + UoW, então há quem ache redundante
  • Um método novo para cada consulta diferente
  • Risco de virar “repositório genérico” que só repassa chamadas
Como falar: “Os repositórios escondem o EF Core da Application e centralizam o filtro por restaurante. O commit fica no SaveChangesAsync, que funciona como Unit of Work.”
Design pattern · Criacional

Factory Method

Um método estático que cria o objeto no lugar do new. Ele valida tudo antes de devolver, então o objeto já nasce válido.

public static Product Create(string name, string? description, decimal price,
    Guid categoryId, DateTime createdAt, int initialQuantity = 0, Guid? restaurantId = null)
{
    ValidateName(name);
    ValidatePrice(price);
    ValidateCategoryId(categoryId);
    ValidateQuantity(initialQuantity);

    return new Product { Name = name.Trim(), Price = price, /* ... */ };
}

Repare: createdAt vem de fora. A entidade nunca chama DateTime.UtcNow (ver IClock).

Prós
  • Nome expressivo (Create)
  • Validação garantida na criação
  • Construtor privado fica livre para o EF Core
Contras
  • Muitos parâmetros podem confundir a ordem (parâmetros obrigatórios precisam vir antes dos opcionais)
Design pattern · Estrutural

Adapter / Ponte (IIdentityService)

O Adapter converte uma interface que você não controla (o UserManager<ApplicationUser> do Identity) para uma interface simples que a sua aplicação define.

// Application: só tipos primitivos, nada de ApplicationUser
public interface IIdentityService
{
    Task<bool> EmailExistsAsync(string email, CancellationToken ct);
    Task<AuthenticatedUser?> ValidateCredentialsAsync(string email, string password, CancellationToken ct);
    Task<IList<string>> GetRolesAsync(Guid userId, CancellationToken ct);
}

// Infrastructure: IdentityService usa UserManager por baixo

O mesmo vale para IJwtTokenGenerator, ICurrentUserService e IClock: interfaces pequenas na Application, implementação concreta na Infrastructure.

Prós
  • Application não conhece tipos do Identity
  • Trocar o Identity por outro provedor mexe só na Infrastructure
Contras
  • Mais uma camada para manter quando o Identity ganha recurso novo
Design pattern · Dados

DTO + projeto Contracts

DTO (Data Transfer Object) é um objeto só de dados, usado para entrar e sair da API. A entidade de domínio nunca é devolvida direto no JSON.

// Contracts/Products/ProductDetailsDto.cs
public record ProductDetailsDto(Guid Id, string Name, string? Description, decimal Price,
    int QuantityInStock, Guid CategoryId, string CategoryName, DateTime CreatedAt);

Ficam num projeto separado, Contracts, referenciado por Application, Infrastructure e Api.

Prós
  • Não vaza campos internos nem cria loops de serialização
  • Contrato da API estável mesmo se a entidade mudar
  • Poderia virar um pacote para clientes .NET
Contras
  • Mapeamento manual entidade → DTO
  • Mais classes parecidas entre si

Design pattern · Organização

Endpoint Modules

Cada entidade tem uma classe que implementa IEndpointModule e mapeia suas rotas. O Program.cs só percorre uma lista.

public interface IEndpointModule
{
    IEndpointRouteBuilder MapEndpoints(IEndpointRouteBuilder app);
}

// Program.cs
IEndpointModule[] endpointModules =
[
    new ProductEndpointsModule(), new CategoryEndpointsModule(),
    new SupplierEndpointsModule(), new StockMovementEndpointsModule(),
    new AuthEndpointsModule(), new RestaurantEndpointsModule()
];
foreach (var module in endpointModules) module.MapEndpoints(app);

A lista é escrita à mão (sem reflection) para ficar óbvio quais módulos existem.

Prós
  • Program.cs curto
  • Rotas de um módulo num arquivo só
  • Sem “mágica” de descoberta automática
Contras
  • Esquecer de adicionar um módulo novo na lista = rotas não existem
Design pattern · Testabilidade

Abstração do relógio (IClock)

DateTime.UtcNow é uma dependência escondida: cada execução dá um valor diferente e o teste não consegue prever. A solução é injetar o “agora”.

public class Clock : IClock
{
    private readonly TimeProvider _timeProvider;
    public DateTime UtcNow => _timeProvider.GetUtcNow().UtcDateTime;
}

// Nos testes:
public class FakeClock : IClock
{
    public DateTime UtcNow => new(2026, 1, 1, 12, 0, 0, DateTimeKind.Utc);
}

O Handler pede o IClock e passa a data para o domínio (CreatedAt, MovementDate). O domínio nunca lê o relógio sozinho.

Prós
  • Testes com data fixa e previsível
  • Domínio puro, sem efeito colateral
Contras
  • Mais um parâmetro e mais uma injeção
  • O próprio .NET já tem TimeProvider; o IClock é uma camada fina por cima
Princípios

SOLID com exemplos do projeto

LetraPrincípioOnde aparece
SSingle Responsibility: uma classe, um motivo para mudar.CreateProductHandler só cria produto. CreateProductCommandValidator só valida. ProductRepository só acessa dados. O endpoint só traduz HTTP.
OOpen/Closed: aberto para extensão, fechado para modificação.Para criar um caso de uso novo, você adiciona um Command + Handler; nada existente muda. Um behavior novo no MediatR vale para todos sem editar Handler nenhum. Um módulo novo entra na lista de IEndpointModule.
LLiskov Substitution: uma implementação pode substituir outra sem quebrar.FakeProductRepository substitui ProductRepository nos testes, e FakeClock substitui Clock. O Handler funciona igual com qualquer um.
IInterface Segregation: interfaces pequenas e específicas.IApplicationDbContext foi enxugado para só SaveChangesAsync. IClock só tem UtcNow. ICurrentUserService só tem RestaurantId. Um repositório por entidade, não um gigante.
DDependency Inversion: dependa de abstrações, não de implementações.Handlers recebem IProductRepository, IClock, IIdentityService. Quem escolhe a implementação é o container de DI, na Infrastructure.
Como falar: “O D é o mais visível: a Application define interfaces e a Infrastructure implementa. O I aparece quando enxuguei o IApplicationDbContext para só SaveChangesAsync. O L é o que permite trocar repositórios reais por Fakes nos testes.”
Princípios

DRY, KISS, YAGNI, Fail Fast

  • DRY (Don’t Repeat Yourself): o nome da claim "restaurantId" é uma constante única em CurrentUserService, usada também pelo gerador de JWT. As roles moram em RoleNames.
  • KISS (Keep It Simple): lista de módulos escrita à mão em vez de reflection; CQRS leve, sem bancos separados.
  • YAGNI (You Aren’t Gonna Need It): não foi criado o padrão Result<T> nem Event Sourcing, porque o projeto não precisava.
  • Fail Fast: a validação roda antes do Handler, e a entidade lança exceção no primeiro dado inválido.
  • Separation of Concerns: HTTP na Api, regras no Domain, persistência na Infrastructure.
ASP.NET Core

Injeção de Dependência (DI)

O que é

A classe declara o que precisa no construtor e o container do .NET entrega pronto. Ninguém dá new ProductRepository(...) na mão.

Tempos de vida (lifetimes)

LifetimeQuando criaNo projeto
SingletonUma vez para a aplicação inteiraTimeProvider.System, IClock (não guardam estado por requisição)
ScopedUma vez por requisição HTTPAppDbContext, todos os repositórios, IIdentityService, ICurrentUserService, IJwtTokenGenerator
TransientUma nova a cada pedidoHandlers e validators (padrão do MediatR/FluentValidation)

Repositórios são Scoped porque usam o AppDbContext, que também é Scoped. Um Singleton nunca deve depender de um Scoped (erro de “captive dependency”).

No projeto

// Program.cs só chama dois métodos de extensão:
builder.Services.AddApplication();
builder.Services.AddInfrastructure(builder.Configuration);

// Infrastructure/DependencyInjection.cs
services.AddScoped<IProductRepository, ProductRepository>();
services.AddScoped<IApplicationDbContext>(p => p.GetRequiredService<AppDbContext>());
services.AddSingleton<IClock, Clock>();

Detalhe: no Program.cs, o seed de roles cria um scope manual (app.Services.CreateScope()) porque o RoleManager é Scoped e ali ainda não existe uma requisição.

Prós
  • Baixo acoplamento
  • Testes trocam implementações facilmente
  • Configuração centralizada por camada
Contras
  • Erros de registro só aparecem em tempo de execução
  • Lifetime errado causa bugs difíceis (ex.: DbContext compartilhado entre requisições)
Como falar: “Cada camada tem seu AddApplication/AddInfrastructure. DbContext e repositórios são Scoped, um por requisição; o relógio é Singleton porque não tem estado.”
ASP.NET Core

Middleware e pipeline HTTP

O que é

Middleware é um componente que fica no caminho de toda requisição. Eles formam uma fila: cada um pode agir e passar para o próximo, ou responder e parar ali. A ordem importa.

flowchart LR
  R[Requisição] --> E[ExceptionHandler]
  E --> C[CORS]
  C --> AN[Authentication]
  AN --> AZ[Authorization]
  AZ --> EP[Endpoint]

app.UseValidationExceptionHandling(); // 1º: pega exceções de tudo que vem depois
app.UseCors(FrontendCorsPolicy);      // antes da auth: o preflight OPTIONS não tem token
app.UseAuthentication();              // descobre QUEM é (lê o JWT)
app.UseAuthorization();               // decide SE pode (role, policy)
  • Exception handler primeiro, para envolver tudo que roda depois.
  • CORS antes da autenticação, senão o preflight seria barrado por falta de token.
  • Authentication antes de Authorization: não dá para decidir permissão sem saber quem é.
Prós
  • Preocupações globais num lugar só
  • Endpoints não repetem checagens
Contras
  • Ordem errada causa bugs silenciosos
  • Fluxo menos explícito para quem lê só o endpoint
Middleware × Pipeline Behavior: middleware roda para toda requisição HTTP; behavior roda para todo Command/Query do MediatR. Um é da Api, o outro é da Application.
ASP.NET Core

Tratamento de erros centralizado

As camadas internas só lançam exceções com significado. Um middleware único converte cada tipo num status HTTP no formato ProblemDetails (RFC 7807).

ExceçãoQuem lançaHTTP
ValidationExceptionValidationBehavior / Identity400 com erros por campo
DomainExceptionEntidades e Handlers (ex.: estoque insuficiente)400
InvalidCredentialsExceptionLoginHandler401
NotFoundExceptionHandlers404
Qualquer outraBug500
if (exception is DomainException domainException)
{
    await Results.Problem(detail: domainException.Message,
        statusCode: StatusCodes.Status400BadRequest).ExecuteAsync(context);
    return;
}
Prós
  • Sem try/catch em cada endpoint
  • Respostas de erro padronizadas
Contras
  • Exceções custam desempenho e são usadas para fluxo esperado
  • Alternativa seria o padrão Result<T>, que foi descartado de propósito
ASP.NET Core

Validação em duas camadas

A mesma regra (“preço não negativo”) aparece no validator e na entidade. Não é duplicação à toa:

FluentValidation (Application)Entidade (Domain)
ValidaA requisiçãoO estado do objeto
ErrosTodos de uma vez, por campoPara no primeiro
Pode consultar banco?Sim (ex.: e-mail já existe)Não
PapelMensagem amigável ao clienteÚltima linha de defesa
public class CreateProductCommandValidator : AbstractValidator<CreateProductCommand>
{
    public CreateProductCommandValidator()
    {
        RuleFor(c => c.Name).NotEmpty().MaximumLength(150);
        RuleFor(c => c.Price).GreaterThanOrEqualTo(0);
        RuleFor(c => c.CategoryId).NotEqual(Guid.Empty);
    }
}

Multi-tenant (vários restaurantes)

O que é

Uma API e um banco atendendo vários clientes (tenants), cada um vendo só os próprios dados. Aqui o modelo é banco compartilhado com coluna discriminadora (RestaurantId em cada tabela).

Como funciona no projeto

  1. No cadastro, cria-se um Restaurant e o usuário é ligado a ele.
  2. O JWT carrega a claim restaurantId.
  3. ICurrentUserService lê essa claim do HttpContext.
  4. Todo repositório filtra por ela, e todo Create grava ela.
public Guid? RestaurantId
{
    get
    {
        var claimValue = _httpContextAccessor.HttpContext?.User
            .FindFirst(RestaurantIdClaimType)?.Value;
        return Guid.TryParse(claimValue, out var id) ? id : null;
    }
}

Buscar por Id um produto de outro restaurante devolve null, e o Handler responde 404. A API nem confirma que o registro existe. Isso é coberto pelos testes de isolamento.

Prós
  • Um deploy e um banco para todos (barato)
  • Filtro centralizado nos repositórios
Contras
  • Esquecer o filtro em um lugar = vazamento de dados
  • Alternativa mais automática: Global Query Filter do EF Core
  • Isolamento mais forte exigiria schema ou banco por tenant
Como falar: “É multi-tenant com banco compartilhado e coluna RestaurantId. O tenant vem de uma claim do JWT, lida por um ICurrentUserService, e os repositórios aplicam o filtro. Tenho testes que provam que um restaurante não lê dados do outro.”

EF Core: o que é, DbContext e DbSet

O que é

Entity Framework Core é um ORM (Object-Relational Mapper). Ele traduz classes C# em tabelas e consultas LINQ em SQL. Você escreve _context.Products.Where(...) e ele gera e executa o SELECT no SQL Server.

As três peças principais

PeçaPara que serveNo projeto
DbContextA “sessão” com o banco. Guarda conexão, mapeamento e o controle do que mudou. Tem o SaveChangesAsync.AppDbContext (herda de IdentityDbContext)
DbSet<T>Representa uma tabela. É o ponto de partida de toda consulta e de todo Add/Remove.Products, Categories, Suppliers, StockMovements, Restaurants
ProviderO “tradutor” para um banco específico.UseSqlServer na API, UseInMemoryDatabase nos testes
Infrastructure/Persistence/AppDbContext.cs
public class AppDbContext : IdentityDbContext<ApplicationUser, ApplicationRole, Guid>, IApplicationDbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<Product> Products => Set<Product>();
    public DbSet<Category> Categories => Set<Category>();
    // ... Suppliers, StockMovements, Restaurants

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        base.OnModelCreating(modelBuilder);   // 1º: monta as tabelas do Identity
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly); // 2º: as nossas
    }
}
  • OnModelCreating roda uma vez e monta o “modelo”: qual classe vira qual tabela, quais colunas, quais relações.
  • ApplyConfigurationsFromAssembly procura todas as classes IEntityTypeConfiguration<T> (pasta Configurations/) e aplica, sem precisar listar uma por uma.
  • base.OnModelCreating vem antes porque é ele que ensina o EF a mapear as 7 tabelas AspNet*.
  • O AppDbContext também implementa IApplicationDbContext, que só expõe SaveChangesAsync. É assim que a Application salva sem conhecer o EF Core.

Registro no DI

services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString)                              // provider + connection string
           .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking)); // leituras sem rastreamento

services.AddScoped<IApplicationDbContext>(p => p.GetRequiredService<AppDbContext>());

AddDbContext registra o contexto como Scoped: um por requisição. O DbContext não é thread-safe, então nunca deve ser compartilhado entre requisições (Singleton seria um bug).

Como falar: “O AppDbContext é o Unit of Work, cada DbSet é uma tabela, e o mapeamento fica em classes de configuração separadas, aplicadas com ApplyConfigurationsFromAssembly.”

Fluent API: mapeando entidades para tabelas

Existem duas formas de dizer ao EF como é a tabela: atributos na entidade ([MaxLength(150)]) ou Fluent API numa classe separada. O projeto usa Fluent API para o Domain continuar sem nenhuma referência ao EF Core.

Infrastructure/Persistence/Configurations/ProductConfiguration.cs
public class ProductConfiguration : IEntityTypeConfiguration<Product>
{
    public void Configure(EntityTypeBuilder<Product> builder)
    {
        builder.ToTable("Products");                  // nome da tabela
        builder.HasKey(p => p.Id);                    // chave primária

        builder.Property(p => p.Name)
            .HasMaxLength(150)                        // NVARCHAR(150)
            .IsRequired();                            // NOT NULL

        builder.Property(p => p.Price)
            .HasPrecision(10, 2);                     // DECIMAL(10,2)

        builder.HasOne(p => p.Category)               // um Product tem UMA Category
            .WithMany(c => c.Products)                // uma Category tem MUITOS Products
            .HasForeignKey(p => p.CategoryId)         // ligados pela coluna CategoryId
            .IsRequired();                            // relação obrigatória
    }
}

Detalhes que combinam com DDD

  • Construtor privado: private Product() { } existe só para o EF conseguir montar o objeto ao ler do banco. O código do dia a dia usa Product.Create(...).
  • private set: o EF consegue preencher propriedades com setter privado. Ninguém de fora consegue.
  • Coleção protegida: Category expõe IReadOnlyCollection<Product> Products, mas guarda num campo privado _products. Essa linha manda o EF ler e escrever direto no campo:
// Domain/Entities/Category.cs
private readonly List<Product> _products = new();
public IReadOnlyCollection<Product> Products => _products.AsReadOnly();

// CategoryConfiguration.cs
builder.Navigation(c => c.Products)
    .UsePropertyAccessMode(PropertyAccessMode.Field);
  • Enums (StockMovementType) são gravados como INT por padrão, sem configuração. No JSON viram texto por causa do JsonStringEnumConverter, mas isso é da API, não do banco.
  • Id gerado no C#: a classe base Entity faz Id = Guid.NewGuid() no construtor. O Id já existe antes de salvar, por isso o Handler devolve product.Id logo depois do SaveChangesAsync.
  • RestaurantId sem relação: mapeado só com builder.Property(p => p.RestaurantId), sem HasOne. A FK existe no banco (script SQL), mas o EF trata como um Guid simples.
Prós
  • Domain limpo, sem atributos de banco
  • Uma classe de configuração por entidade, fácil de achar
  • Fluent API faz coisas que atributos não fazem (acesso por campo, relações complexas)
Contras
  • A regra fica longe da entidade: precisa abrir dois arquivos
  • Sem migrations, se a configuração e o script SQL divergirem, o erro só aparece em execução
Dados · EF Core 3/6

Change Tracker, NoTracking e Add/Update/Remove

O que é o Change Tracker

Por padrão, todo objeto que o EF lê do banco fica “vigiado” pelo Change Tracker. Ele guarda uma cópia dos valores originais e, no SaveChangesAsync, compara para descobrir o que mudou e gerar os INSERT/UPDATE/DELETE.

EstadoSignificaSQL no SaveChanges
DetachedO EF não está vigiandonada
UnchangedVigiado, sem mudançanada
AddedNovo, precisa inserirINSERT
ModifiedMudou, precisa atualizarUPDATE
DeletedPrecisa apagarDELETE

O NoTracking global (configurado na raiz)

options.UseSqlServer(connectionString)
       .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);

Essa linha, no AddInfrastructure, faz toda consulta voltar sem rastreamento, como se cada uma tivesse .AsNoTracking() no final. Os objetos chegam Detached.

  • Por que: a maioria das consultas é só leitura (listar, buscar por Id). Sem rastreamento, o EF não guarda cópia nem compara nada: gasta menos memória e CPU.
  • Consequência: se você alterar um objeto lido e chamar SaveChangesAsync, nada acontece, porque o EF nem sabe que ele existe. Por isso os repositórios avisam explicitamente.

Escritas explícitas nos repositórios

public void Add(Product product)    => _context.Products.Add(product);     // estado Added
public void Remove(Product product) => _context.Products.Remove(product);  // estado Deleted
public void Update(Product product) => _context.Entry(product).State = EntityState.Modified;

Nada vai ao banco nessas linhas. Elas só mudam o estado no Change Tracker. Tudo é gravado junto, numa transação, quando o Handler chama await _context.SaveChangesAsync(ct).

DbSet.Update() × Entry().State = Modified

As duas marcam como alterado, mas com alcance diferente:

_context.Products.Update(product)_context.Entry(product).State = Modified
AlcancePercorre o grafo inteiro (produto + Category carregada pelo Include)Só o próprio produto
Risco“Fixup”: a navegação antiga sobrescreve a FK novaNenhum nesse cenário

Foi o bug da Etapa 22c: trocar a categoria do produto não salvava, porque product.Category ainda apontava para a categoria antiga e o EF “corrigia” o CategoryId de volta.

Prós do NoTracking global
  • Leituras mais rápidas e leves
  • Escrita explícita deixa claro o que vai ser salvo
  • Sem mudança “acidental” salva por engano
Contras
  • Esquecer o Update/Remove = mudança perdida em silêncio
  • Modified manual gera UPDATE de todas as colunas, não só das que mudaram
  • Precisa entender estados do Change Tracker para depurar
Como falar: “Configurei NoTracking como padrão global porque a maioria das consultas é leitura. Em troca, os repositórios marcam as escritas explicitamente com Add, Remove e Entry().State = Modified, e o SaveChangesAsync grava tudo numa transação.”

Consultas LINQ: Where, Include, Skip/Take e companhia

IQueryable: a consulta é montada antes de executar

_context.Products é um IQueryable<Product>. Cada .Where, .OrderBy, .Skip só adiciona um pedaço à consulta. Nada vai ao banco até um método que materializa o resultado (ToListAsync, FirstOrDefaultAsync, CountAsync, AnyAsync). Isso se chama execução adiada (deferred execution).

Infrastructure/Persistence/Repositories/ProductRepository.cs → GetPagedAsync
var query = _context.Products
    .Include(p => p.Category)                                   // traz a categoria junto (JOIN)
    .Where(p => p.RestaurantId == _currentUserService.RestaurantId); // filtro do tenant

if (!string.IsNullOrWhiteSpace(name))
    query = query.Where(p => p.Name.Contains(name));            // filtro opcional

if (categoryId.HasValue)
    query = query.Where(p => p.CategoryId == categoryId.Value);

var totalCount = await query.CountAsync(ct);                    // 1ª ida ao banco: SELECT COUNT(*)

var items = await ApplySort(query, sortBy, sortDirection)
    .Skip((page - 1) * pageSize)                                // pula as páginas anteriores
    .Take(pageSize)                                             // pega só esta página
    .ToListAsync(ct);                                           // 2ª ida ao banco: SELECT ... OFFSET/FETCH

Os filtros opcionais funcionam porque a consulta ainda não rodou: o if decide se aquele WHERE entra ou não no SQL final.

Cada método e o SQL que ele vira

Por que o Count vem antes do Skip/Take

O frontend precisa saber quantos produtos existem no total (com os filtros) para montar a paginação. Se contasse depois do Take(10), o total seria no máximo 10.

Ordem importa: OrderBy antes de Skip

Sem ordem definida, o SQL Server pode devolver as linhas em qualquer ordem, e a página 2 pode repetir itens da página 1. Por isso o ApplySort sempre tem um caso padrão (OrderBy(Name)).

Filtrar no banco × filtrar na memória

No GetProductsHandler existe um .Select(...), mas ele roda depois do ToListAsync, sobre a lista já em memória (LINQ to Objects). Só converte entidade em DTO, sem SQL.

var items = products                       // List<Product> já carregada
    .Select(p => new ProductListItemDto(p.Id, p.Name, p.Price,
        p.QuantityInStock, p.CategoryId, p.Category!.Name, p.CreatedAt))
    .ToList();

Regra de ouro: filtros e paginação sempre no IQueryable, antes do ToListAsync. Se fizer ToListAsync() e depois Where, o banco devolve a tabela inteira e o filtro roda na memória.

Async e CancellationToken

Todo método que vai ao banco é ...Async e recebe o CancellationToken. Enquanto o SQL Server responde, a thread fica livre para atender outras requisições. Se o cliente desistir (fechou a aba), o token cancela a consulta.

Como falar: “As consultas são montadas em IQueryable, com filtros opcionais aplicados por if, e só executam no CountAsync e no ToListAsync. A paginação vira OFFSET/FETCH no SQL, e o Include vira um JOIN.”
